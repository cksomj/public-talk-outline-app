# 골자 자동 반영 도구 (update_talk.py)

새/수정된 골자 원본(.docx)을 앱(`public-talk-outline-app/index.html`)의
TALKS 데이터에 자동으로 반영합니다. 기존 번호는 교체(업데이트), 없는 번호는
새로 추가합니다.

## 가장 간단한 사용법

1. 새 골자 `.docx` 파일을 `PublicTalkOutlineApp\new_talks\` 폴더에 넣습니다.
   (파일명은 `S-34_KO_195.docx`처럼 번호가 들어가야 합니다 — 기존 파일과 같은
   형식이면 됩니다.)
2. 아래 명령을 실행합니다.

```
cd D:\Dean_Data\Documents\PublicTalkOutlineApp\tools
python update_talk.py --dir ..\new_talks
```

3. 끝나면 화면에 "no=195: inserted" 또는 "no=50: updated"처럼 결과가 나오고,
   자동으로:
   - `index.html`의 TALKS 데이터가 갱신되고
   - JSON 유효성이 확인되고
   - 로컬 서버로 열어서 해당 번호가 정상 표시되는지 스크린샷이
     `tools\verify_screenshots\talk<번호>.png`에 저장되고
   - git commit(그리고 원격 저장소가 연결돼 있으면 push)까지 됩니다.

## 파일 하나만 반영하고 싶을 때

```
python update_talk.py "경로\S-34_KO_050.docx"
```

여러 개를 한 번에 지정할 수도 있습니다:

```
python update_talk.py "경로\S-34_KO_050.docx" "경로\S-34_KO_195.docx"
```

## 신규 번호를 추가할 때 꼭 알아야 할 것 — 테마 분류

카드마다 색깔/이모지로 표시되는 "테마 분류"(하느님·그리스도, 도덕·행실 등 10개)는
원본 .docx 안에는 없는 정보라서(편집자가 판단해서 정하는 것), 이 도구가 새 번호를
추가할 때 자동으로 알아낼 수 없습니다. **그리고 앱 자체의 "편집" 화면에도 이
테마를 바꾸는 입력란이 없다는 것을 실제로 확인했습니다** — 제목/유의사항/소주제·
내용만 고칠 수 있습니다. 그래서:

- 신규 추가 시 어떤 테마인지 알고 있으면 `--theme 번호`를 같이 주십시오
  (0=하느님·그리스도, 1=마지막 날·예언, 2=가정·자녀, 3=도덕·행실,
  4=성경·진리·종교, 5=기도·영성, 6=구원·부활, 7=전도·봉사, 8=신뢰·믿음·인내,
  9=사회·윤리).

  ```
  python update_talk.py "경로\S-34_KO_195.docx" --theme 3
  ```

- `--theme`을 안 주면 일단 0(하느님·그리스도)으로 채워 넣고(비워 두면 앱이 그
  카드를 열 때 바로 오류가 나는 것을 실제로 확인했습니다), 실행이 끝나면 화면에
  **"[꼭 확인]"**이라고 크게 표시해 줍니다.
- `--theme`은 **이번 실행에서 새로 추가되는 번호에만** 적용됩니다. 같은 실행에
  업데이트 대상(이미 있는 번호)이 섞여 있어도 그 항목들의 테마는 절대 바뀌지
  않습니다(처음엔 이 둘을 분리하지 않아서, 여러 파일을 한 번에 넣었을 때
  `--theme`이 무관한 기존 항목의 테마까지 덮어써 버리는 사고가 실제 테스트
  중에 있었습니다 — 그래서 완전히 분리했습니다).
- 나중에 이미 있는 번호의 테마를 바로잡고 싶으면 `--set-theme NO:번호`를
  쓰십시오(.docx 파일 없이 단독으로 실행 가능, 여러 번 반복 가능):

  ```
  python update_talk.py --set-theme 195:3
  python update_talk.py --set-theme 195:3 --set-theme 196:7
  ```

## 안전 옵션

- `--no-commit`: index.html만 갱신하고 git에는 손대지 않습니다(반영 결과를
  먼저 눈으로 확인하고 싶을 때).
- `--no-push`: commit은 하지만 push는 하지 않습니다(로컬에만 남겨 두고
  싶을 때).
- `--no-screenshot`: 스크린샷 검증을 생략합니다(Chrome/Node가 없는 환경 등).

## 동작 방식(참고)

- 파일명에서 `S-34_KO_XXX.docx`의 `XXX`를 번호로 추출합니다(대소문자,
  하이픈/언더스코어 차이는 자동으로 흡수됩니다).
- .docx 안의 문단을 읽어서 제목 / "연사의 유의 사항"(note) / "(N분)"으로
  끝나는 섹션 제목 / 그 아래 요점(points)들로 나눕니다 — 이 규칙은
  GOLJA-SETUP-AND-SAMPLE-CHECK, GOLJA-FIX-BATCH, GOLJA-FIX-REMAINING
  작업(2026-09-05~06)에서 194개 전체를 실제로 검증하며 확정한 것과 동일한
  규칙입니다. 새로 추측한 부분은 없습니다.
- TALKS 배열에서 같은 `no`가 있으면 그 항목의 `title`/`note`/`sections`만
  교체합니다(다른 필드가 나중에 추가되어 있어도 보존됩니다). 없으면 `no` 순서를
  지켜서 새 항목을 삽입합니다.
- index.html에서 TALKS가 들어 있는 `<script id="DATA" type="application/json">`
  블록만 정확히 교체합니다. 나머지 코드(성구/출판물 링크 기능 등)는 전혀
  건드리지 않습니다.
- 이 도구가 다시 JSON을 쓸 때 원본과 같은 포맷(Python `json.dumps` 콤마+콜론
  뒤 공백 스타일)과 줄바꿈 방식(CRLF)을 그대로 유지합니다 — 이걸 지키지
  않으면 diff가 필요 이상으로 커진다는 것을 GOLJA-FIX-BATCH 작업에서 실제로
  겪었기 때문에 처음부터 이 방식으로 만들었습니다.

## 주의할 점

- **이미 링크가 붙어 있는 성구/출판물 참조는 데이터가 아니라 렌더링 시점에
  `lkA()` 함수가 만듭니다.** 즉 이 도구로 새 골자를 넣으면 그 안의 성구/출판물
  인용도 기존 194개와 똑같이 자동으로 링크가 걸립니다. 별도 작업이 필요
  없습니다.
- **원본 .docx 자체가 문장부호(콜론/괄호 등)를 정상적으로 포함하고 있어야
  합니다.** GOLJA-FIX-REMAINING-20260906-G3에서 겪었듯, 원본 파일 자체가
  손상되어 있으면(예: 콜론/괄호가 전부 빠진 파일) 이 도구도 똑같이 잘못
  파싱합니다 — 원본이 깨끗한지 한 번은 사람이 확인하는 것이 안전합니다.
- git push는 `origin`이라는 이름의 원격 저장소가 연결되어 있을 때만
  시도합니다. 연결되어 있지 않으면 로컬 커밋까지만 하고 멈춥니다.
